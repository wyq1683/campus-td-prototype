## 一、核心循环

```
                        ┌──────────────────────────────────────────┐
                        │                                          │
                        ▼                                          │
   ┌────────────┐  ┌─────────┐  ┌──────────┐  ┌──────────┐  ┌────────────┐
   │  波次开始   │─▶│ 敌人进场 │─▶│ 塔自动开火│─▶│ 结算奖励  │─▶│ 建造/升级  │
   │ 预览 + 倒计时│  │ 沿路径推进│  │ 减速·溅射 │  │ 击杀+清波 │  │ 花金币决策 │
   └────────────┘  └─────────┘  └──────────┘  └──────────┘  └────────────┘
                          │                         │
                          │ 敌人抵达基地             │ 金币
                          ▼                         │
                   ┌─────────────┐                  │
                   │ 扣除基地生命  │◀─────────────────┘
                   │ 生命=0 → 失败 │
                   └─────────────┘
```

**循环节拍**：`观察路径 → 花金币 → 看结果 → 再决策`，单波时长 5–102s，10 波一局约 8–10 分钟。

**三个决策点**（每波之间）：
1. **建在哪** —— 补盲区 / 叠杀区 / 守基地
2. **建什么** —— BASIC(便宜) / RAPID(高频) / AOE(溅射) / SLOW(减速力场)
3. **升哪座** —— 每次升级成本 = `基础价 × 0.8 × 当前等级`，越升越贵，逼迫取舍

建满 SLOT_A + SLOT_B 后覆盖达 **100%**，此后投入全部转化为叠 DPS。

## 五、数值表

### 5.1 塔

| 类型 | 主题名 | 单发伤害 | 射速/s | DPS | 溅射 | 减速 | 造价 | 定位 |
|---|---|---|---|---|---|---|---|---|
| BASIC | 粉笔盒 | 22 | 1.00 | 22.0 | — | — | 80 | 便宜万金油 |
| RAPID | 试卷连发 | 9 | 3.00 | 27.0 | — | — | 120 | 高频 · 平滑输出 |
| AOE | 拖把横扫 | 30 | 0.70 | 21.0 | 4.0m | — | 150 | 清群 |
| SLOW | 广播操/值日 | 6 | 1.00 | 6.0 | — | 40% / 2.6s | 100 | **全局增益** |

**升级公式**

```
输出塔：  dmg(lv)   = dmg_base × 1.40^(lv-1)
减速塔：  slow(lv)  = min(0.60, 0.40 + 0.05×(lv-1))
          dur(lv)   = 2.6 + 0.4×(lv-1)
通用：    cost(lv)  = int(造价_base × 0.8 × lv)     # lv = 当前等级
```

Excel 等价式（假设造价在 B2、当前等级在 C2）：
```
伤害   = 22 * POWER(1.4, C2-1)
升级费 = INT(B2 * 0.8 * C2)
累计投入 = B2 + SUMPRODUCT(INT(B2*0.8*ROW(INDIRECT("1:"&C2-1))))
```

| 等级 | 累计投入(AOE) | AOE DPS | DPS/100金 |
|---|---|---|---|
| 1 | 150 | 21.0 | 14.0 |
| 2 | 150+120=270 | 29.4 | 10.9 |
| 3 | 270+240=510 | 41.2 | 8.1 |
| 4 | 510+360=870 | 57.6 | 6.6 |
| 5 | 870+480=1350 | 80.7 | 6.0 |

→ **边际收益递减**：等级越高，每金币换到的 DPS 越少。这是防止"一座塔堆到满"的设计意图，
引导玩家横向铺开（建新塔）而非纵向堆高。

## 六、经济模型

**收入**
```
起始金币            = 240
击杀收入            = Σ(敌人 reward)             全程合计 1,710
清波收入            = Σ(28 + 8w), w=1..10        全程合计   720
─────────────────────────────────────────────────────────
全程总收入          = 2,670 金币
```

**支出（熟练玩家路线）**
```
SLOT_A 建 AOE       = 150
SLOT_B 建 RAPID     = 120
SLOT_C 建 SLOW      = 100
SLOT_D 建 AOE       = 150
小计建造            = 520   （占收入 19%）
剩余可升级预算      ≈ 2,150 （占收入 81%）
```

### 6.1 仿真步长必须先收敛，否则整条平衡带是假的

这是本项目踩过的最隐蔽的一个坑，单独记一节以免复发。

`m10_balance.py` 原本用 `DT = 0.1`（0.1 秒一步）。但 **RAPID 射速 3.0 发/秒 → 冷却 0.333s**，
在 0.1 的步长下要等到第 4 步（0.4s）才够开火，**有效射速掉到 2.5，凭空损失约 17% DPS**。

| 步长 | 熟练玩家 | 新手玩家 |
|---|---|---|
| DT = 0.1（错误） | 16/20，漏 2 | 第 9 波崩 |
| DT = 0.05 | 20/20，漏 0 | 2/20 **通关** |
| DT = 0.02 | 20/20，漏 0 | 2/20 **通关** |

DT=0.05 与 0.02 **结果完全一致 → 已收敛**；DT=0.1 那个"看起来很合理"的结果纯粹是量化误差造出来的。
**教训：调数值之前先做步长收敛性检查。** 现在 `DT = 0.05`，并把 0.1 的坑写在代码注释里。

收敛后重新标定（目标：熟练 12–18 生命、新手失败）：

| 血量成长 | 清波奖励 | 熟练玩家 | 新手玩家 |
|---|---|---|---|
| 0.20（旧） | 28+8w | 20/20 漏 0 ✘ 太易 | 2/20 通关 ✘ 太宽容 |
| **0.23（定稿）** | **28+8w** | **16/20 漏 2 ✔** | **第 9 波崩 漏 14 ✔** |
| 0.25 | 28+8w | 10/20 漏 5 ✘ 偏难 | 第 8 波崩 |
| 0.32 | 28+8w | 失败 ✘ | 第 8 波崩 |

### 6.2 平衡带验证

跑 `python campus_td/build/m10_balance.py`：

| 策略 | 建造顺序 | 升级策略 | 结果 | 剩余生命 | 漏怪 |
|---|---|---|---|---|---|
| **熟练玩家** | 补盲区→叠减速→最后防线 | 按 ROI 最大 | **通关** | **16 / 20** | 2 |
| **新手玩家** | 只建最便宜的 BASIC | 按最便宜升级 | **失败**（第 9 波崩） | 0 / 20 | 14 |

**交叉验证**：浏览器端 JS（`campus_td/web/index.html?selftest=1`）跑同一套数值，
结果 `won lives=16 leaks=2`，且漏怪分布与 Python **完全一致**（第 7、8 波各漏 1）。
两份独立实现收敛到同一答案，说明数值移植无误。

**结论**：数值落在目标带内——
- 熟练玩家**险胜但不轻松**（首次破防出现在第 7 波，压力真实）
- 新手**必败**，且失败点在第 8–9 波（玩了 80% 流程才崩，不至于挫败）
- 策略差异带来 **16 点生命差**，说明"建什么/升什么"是真决策，不是假选择

### 7.2 痛点分析

| # | 痛点 | 证据 | 严重度 |
|---|---|---|---|
| P1 | **拐角位被固定塔占满**，玩家塔只能建在直腿（13m 覆盖） | 覆盖率核算：拐角 26m vs 直腿 13m | 高 |

| P3 | 中期（7–8 波）难度尖峰偏陡，新手在此挫败 | 新手策略 80% 流程后崩盘 | 中 |
| P4 | 单局 10 波用时约 8–10 分钟，单波最长 102s，节奏偏拖 | 波次用时表 | 中 |
| P5 | ~~无 HUD（金币/生命/波次不可见）~~ → **已解决**：M10C 的 WebGL2 原型带完整 HUD + 建造/升级交互 | — | ~~高~~ 已闭环 |
| P6 | 敌人种类少、无 Boss 技能，BOSS 只是"血更厚的坦克" | 敌人表 | 低（原型阶段可接受） |

**关于 P2 的澄清**：25% 是**结构上限**而非缺陷——8 座塔平均各覆盖 102m 中的 20m，
数学期望就是 ~25%。不应通过"加密敌人"强行拉高，那样只会让波次时长失控。

### 7.3 优化建议（按优先级）

### 关于 M10C：为什么把 HUD 做进浏览器而不是 Blender

Blender 是建模工具，不是游戏引擎——在里面做 HUD 只能"看"不能"玩"。
M10C 改为产出**独立 WebGL2 页面**（`campus_td/web/index.html`）：

- **GLSL 渲染**：SDF 球体追踪（地面 + 塔柱）+ 解析 ray-AABB（建筑作玻璃体，
  让路径与塔能透出来——本关路径本身就穿过建筑 footprint）+ 屏幕空间敌人光点
  + 建筑足迹 AO / 太阳投影 cookie / 暗角 / ACES 色调映射 / 胶片颗粒
- **JS 跑同一套数值**：与 `m10_balance.py` 逐行对应的战斗/经济/波次逻辑
- **可交互**：拖拽旋转、滚轮缩放、选塔型点空位建造、点已有塔升级、空格提前开波
- **单一数据源**：`campus_td/web/config.js` 由 `m10c_webcfg.py` 从 `m10_config.json` 生成
